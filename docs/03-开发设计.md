## 二、设计概述

### 2.1 设计目标

本文档将总体方案与 PRD 中的需求转化为可编码实现的技术设计，设计目标与 PRD 验收标准（AC1 ~ AC8）逐条对齐：

| 设计目标 | 对齐验收标准 | 量化指标 |
|---|---|---|
| 数据导入完整可靠 | AC1 | 导入诗词 >= 10,000 条，一键脚本可重复执行 |
| 浏览功能可实现 | AC2 | 支持朝代/作者筛选，分页 20 条/页 |
| 搜索性能达标 | AC3 | FTS5 全文搜索响应 <= 500ms |
| 详情页完整展示 | AC4 | 标题、作者、朝代、正文四字段完整渲染 |
| 随机推荐可用 | AC5 | 全量等概率随机，连续 5 次不完全重复 |
| 古典风格界面 | AC6 | 素雅配色、衬线字体、1024px/768px 响应式 |
| 本地可运行 | AC7 | `npm install` + `npm run init-data` + `npm run dev` 三步启动 |
| 代码规范 | AC8 | ESLint 零 error |

### 2.2 设计原则

| 原则 | 说明 |
|---|---|
| 分层架构 | 后端严格分为路由层、业务层、数据访问层，职责单一，便于测试与扩展 |
| 前后端分离 | 前端 SPA 与后端 REST API 独立开发、独立启动，通过 JSON 交互 |
| 可读性优先 | 代码风格清晰直观，关键逻辑必须注释，命名语义化 |
| 数据驱动 | 前端状态由后端 API 驱动，不做复杂的前端状态管理 |
| 渐进增强 | MVP 先保证功能可用，样式与体验可迭代优化 |

#### 3.2.2 组件划分原则

- **页面组件（views/）**：与路由一一对应，负责数据获取与页面级布局
- **通用组件（components/）**：无路由关联的可复用 UI 组件，通过 props 接收数据
- **API 层（api/）**：集中封装所有后端请求，页面组件不直接调用 fetch

#### 3.2.3 路由设计

详见 3.2.1 中 `router/index.js`，具体路由表见第 7 章 7.3 节。

#### 3.2.4 状态管理

MVP 阶段不引入 Pinia/Vuex 等状态管理库。原因：
- 应用无跨页面共享的复杂状态
- 各页面数据由 API 获取后直接渲染
- 随机推荐的"最近展示 ID 列表"使用组件内 `ref` 即可

#### 3.3.2 分层职责

| 层次 | 文件 | 职责 | 不做什么 |
|---|---|---|---|
| 路由层 | `routes/*.js` | 解析请求参数、调用业务层、格式化响应 | 不写 SQL、不做业务判断 |
| 业务层 | `services/*.js` | 组装查询条件、数据转换、分页计算 | 不直接操作 HTTP 请求/响应 |
| 数据访问层 | `dao/*.js` | 编写并执行 SQL、返回原始数据 | 不做数据格式转换 |

#### 3.3.3 中间件设计

```
请求 → [cors] → [json解析] → [静态文件服务] → 路由处理
                                          ↓
                                    [错误处理中间件]
                                          ↓
                                    统一错误响应
```

| 中间件 | 说明 |
|---|---|
| `cors()` | 允许前端开发服务器跨域请求 |
| `express.json()` | 解析 JSON 请求体（MVP 阶段主要用于错误处理统一） |
| `express.static('dist')` | 生产模式下服务前端构建产物 |
| 错误处理中间件 | 捕获所有异常，返回统一错误格式 `{ code, message }` |

### 3.4 数据流设计

#### 3.4.1 数据导入流（一次性）

```
chinese-poetry GitHub 仓库
    │
    ▼  git clone --depth 1（或 npm run init-data 自动触发下载）
data/chinese-poetry/           # 本地数据集目录（gitignore）
    ├── 唐诗/
    │   ├── 唐诗三百首.json
    │   └── 全唐诗.json（按卷拆分多个文件）
    └── 宋词/
        ├── 宋词三百首.json
        └── 全宋词.json
    │
    ▼  Node.js ETL 脚本（npm run init-data）
    │
    │  1. 读取 JSON 文件
    │  2. 字段映射统一（rhythmic→title, paragraphs→content）
    │  3. 过滤无效记录（空标题、空正文）
    │  4. 去重（title + author 组合键）
    │  5. 提取朝代 → INSERT dynasties
    │  6. 提取作者 → INSERT authors（去重）
    │  7. 组装诗词 → 批量 INSERT poems（事务）
    │  8. 构建 FTS5 索引
    │
    ▼
data/poetry.db                 # SQLite 数据库文件
```

#### 3.4.2 运行时查询流

```
用户操作（点击/搜索/翻页）
    │
    ▼  浏览器
Vue 组件调用 api.getPoems(params)
    │
    ▼  fetch GET /api/poems?page=1&dynasty=唐
Express 路由层（poem-routes.js）
    │  解析 query 参数，校验类型
    ▼
业务层（poem-service.js）
    │  组装查询条件 { dynasty: '唐' }，计算 offset
    ▼
数据访问层（poem-dao.js）
    │  SELECT ... FROM poems JOIN authors ... WHERE dynasty = ? LIMIT ? OFFSET ?
    ▼
SQLite（better-sqlite3 同步调用）
    │  返回 rows[]
    ▼
数据逐层返回 → 业务层格式化 → 路由层封装响应
    │
    ▼  JSON 响应
Vue 组件接收数据 → 渲染列表
```

## 四、数据库设计

### 4.1 表结构设计

#### 4.1.1 `dynasties` 表（朝代字典表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 朝代自增主键 |
| `name` | TEXT | NOT NULL UNIQUE | 朝代名称（如"唐"、"宋"、"五代"） |
| `sort_order` | INTEGER | NOT NULL DEFAULT 0 | 排序序号，用于按历史顺序展示 |

```sql
CREATE TABLE dynasties (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL UNIQUE,
    sort_order INTEGER NOT NULL DEFAULT 0
);
```

#### 4.1.2 `authors` 表（作者表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 作者自增主键 |
| `name` | TEXT | NOT NULL | 作者姓名 |
| `dynasty_id` | INTEGER | NOT NULL | 所属朝代，外键关联 dynasties.id |
| `poem_count` | INTEGER | NOT NULL DEFAULT 0 | 收录诗词数量（冗余字段，加速查询） |

| 约束 | 字段 | 说明 |
|---|---|---|
| UNIQUE | (name, dynasty_id) | 同一朝代下作者名不重复 |
| FOREIGN KEY | dynasty_id → dynasties(id) | 关联朝代 |

```sql
CREATE TABLE authors (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL,
    dynasty_id INTEGER NOT NULL,
    poem_count INTEGER NOT NULL DEFAULT 0,
    UNIQUE (name, dynasty_id),
    FOREIGN KEY (dynasty_id) REFERENCES dynasties(id)
);
```

#### 4.1.3 `poems` 表（诗词主表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | 诗词唯一标识（保留数据源 ID，如 "tang-001"） |
| `title` | TEXT | NOT NULL | 诗词标题 |
| `author_id` | INTEGER | NOT NULL | 作者 ID，外键关联 authors.id |
| `dynasty_id` | INTEGER | NOT NULL | 朝代 ID，外键关联 dynasties.id |
| `category` | TEXT | DEFAULT '' | 分类（诗体/词牌名，如"五言绝句"、"水调歌头"） |
| `content` | TEXT | NOT NULL | 诗词正文（各行以 `\n` 分隔） |
| `annotation` | TEXT | DEFAULT '' | 注释（可选字段，数据源中如有则导入） |
| `source` | TEXT | DEFAULT '' | 数据来源标识（如 "tangshi"、"songci"） |

| 约束 | 字段 | 说明 |
|---|---|---|
| FOREIGN KEY | author_id → authors(id) | 关联作者 |
| FOREIGN KEY | dynasty_id → dynasties(id) | 关联朝代 |

```sql
CREATE TABLE poems (
    id         TEXT    PRIMARY KEY,
    title      TEXT    NOT NULL,
    author_id  INTEGER NOT NULL,
    dynasty_id INTEGER NOT NULL,
    category   TEXT    DEFAULT '',
    content    TEXT    NOT NULL,
    annotation TEXT    DEFAULT '',
    source     TEXT    DEFAULT '',
    FOREIGN KEY (author_id)  REFERENCES authors(id),
    FOREIGN KEY (dynasty_id) REFERENCES dynasties(id)
);
```

#### 4.1.4 `poem_fts` 虚拟表（FTS5 全文搜索）

```sql
CREATE VIRTUAL TABLE poem_fts USING fts5(
    title,
    author,
    content,
    content='poems',
    content_rowid='rowid'
);
```

| 列 | 说明 |
|---|---|
| `title` | 诗词标题（从 poems 表同步） |
| `author` | 作者姓名（从 authors 表关联获取） |
| `content` | 诗词正文 |

> 注意：FTS5 使用 `content=` 同步模式，以 poems 表的 rowid 为关联键。由于 poems 主键为 TEXT 类型，需额外维护一个 rowid 映射。实际实现中采用外部内容模式的变体：使用触发器在 poems 表 INSERT/DELETE 时同步 poem_fts。

**替代方案（推荐）**：由于 poems 表主键为 TEXT，FTS5 content 同步较复杂，改用独立 FTS5 表：

```sql
CREATE VIRTUAL TABLE poem_fts USING fts5(
    poem_id TOKENIZE 'unicode61',
    title   ,
    author  ,
    content ,
    tokenize = 'unicode61'
);
```

在数据导入时同步写入 poem_fts，查询时通过 poem_id 关联 poems 表获取完整数据。

### 4.2 ER 图

```
┌──────────────┐       ┌──────────────────┐       ┌───────────────────┐
│   dynasties  │       │     authors      │       │      poems        │
├──────────────┤       ├──────────────────┤       ├───────────────────┤
│ id (PK)      │◄──┐   │ id (PK)          │◄──┐   │ id (PK, TEXT)     │
│ name (UNIQUE)│   │   │ name             │   │   │ title             │
│ sort_order   │   └───│ dynasty_id (FK)  │   └───│ author_id (FK)    │
└──────────────┘       │ poem_count       │       │ dynasty_id (FK)   │
                       └──────────────────┘       │ category          │
                                                  │ content (TEXT)     │
                       ┌──────────────────┐       │ annotation        │
                       │    poem_fts      │       │ source            │
                       │  (FTS5 虚拟表)    │       └───────────────────┘
                       ├──────────────────┤
                       │ poem_id          │──────────► poems.id
                       │ title            │
                       │ author           │
                       │ content          │
                       └──────────────────┘
```

关系说明：
- `dynasties` 1 : N `authors`（一个朝代有多个作者）
- `authors` 1 : N `poems`（一个作者有多首诗词）
- `dynasties` 1 : N `poems`（一个朝代有多首诗词）
- `poems` 1 : 1 `poem_fts`（一首诗词对应一条全文索引记录）

### 4.3 索引策略

| 索引 | 表 | 字段 | 类型 | 原因 |
|---|---|---|---|---|
| `idx_poems_author_id` | poems | author_id | B-Tree | 按作者筛选诗词，高频查询 |
| `idx_poems_dynasty_id` | poems | dynasty_id | B-Tree | 按朝代筛选诗词，高频查询 |
| `idx_poems_category` | poems | category | B-Tree | 按诗体/词牌筛选 |
| `idx_poems_title` | poems | title | B-Tree | 标题排序与精确查找 |
| `idx_authors_dynasty_id` | authors | dynasty_id | B-Tree | 按朝代筛选作者列表 |
| `idx_authors_name` | authors | name | B-Tree | 按作者名查找 |
| `poem_fts` | poem_fts | title + author + content | FTS5 全文索引 | 关键词全文搜索，核心性能保障 |

> dynasties 表数据量极小（< 20 条），无需额外索引。authors 表的 `UNIQUE(name, dynasty_id)` 约束自动创建复合索引，`idx_authors_name` 用于单独按姓名查询的场景。

### 4.4 数据量预估与性能考量

| 表 | 预估记录数 | 单行大小（估） | 总大小（估） |
|---|---|---|---|
| dynasties | ~10 | ~50 B | < 1 KB |
| authors | ~12,000 | ~100 B | ~1.2 MB |
| poems | ~78,000（唐诗 57k + 宋词 21k） | ~500 B | ~39 MB |
| poem_fts | ~78,000 | ~600 B | ~47 MB |

**数据库文件总大小预估**：~90 MB（含索引），SQLite 单文件完全可承载。

**性能考量：**

| 场景 | 预估耗时 | 保障措施 |
|---|---|---|
| 列表分页查询 | < 50ms | 索引覆盖筛选字段，LIMIT/OFFSET 分页 |
| FTS5 全文搜索 | < 200ms | FTS5 全文索引，远优于 LIKE 模糊查询 |
| 随机查询 | < 100ms | 优化策略见 5.6 节 |
| 作者列表查询 | < 20ms | 索引覆盖，数据量小 |

## 五、接口设计（详细）

### 5.1 统一响应格式

所有 API 响应遵循统一格式：

**成功响应：**
```json
{
  "code": 0,
  "data": { ... }
}
```

**错误响应：**
```json
{
  "code": 400,
  "message": "请求参数错误：page 必须为正整数"
}
```

| code | 含义 | 说明 |
|---|---|---|
| 0 | 成功 | 请求处理成功 |
| 400 | 请求参数错误 | 参数缺失、类型错误等 |
| 404 | 资源不存在 | 诗词 ID 无效等 |
| 500 | 服务器内部错误 | 数据库异常等未预期错误 |

### 5.2 GET `/api/poems` — 获取诗词列表

**请求示例：**

```bash
curl "http://localhost:3000/api/poems?page=1&pageSize=20&dynasty=唐&author=李白"
```

**请求参数：**

| 参数 | 类型 | 必填 | 默认值 | 校验规则 |
|---|---|---|---|---|
| page | number | 否 | 1 | 正整数，>= 1 |
| pageSize | number | 否 | 20 | 正整数，范围 [1, 100] |

**RANDOM() 性能优化方案：**

直接使用 `ORDER BY RANDOM() LIMIT 1` 在 78,000 条记录下需全表排序，耗时可能超过 200ms。采用以下优化策略：

```sql
-- 方案：先获取随机 rowid，再精确查询
-- 步骤 1：获取总记录数（可缓存）
SELECT COUNT(*) AS cnt FROM poems;

-- 步骤 2：生成随机偏移量（在 Node.js 中计算）
-- offset = Math.floor(Math.random() * cnt)

-- 步骤 3：通过 rowid 偏移获取
SELECT p.id, p.title, a.name AS author, d.name AS dynasty,
       p.category, p.content
FROM poems p
JOIN authors a ON p.author_id = a.id
JOIN dynasties d ON p.dynasty_id = d.id
WHERE p.rowid = @randomRowid
LIMIT 1;
```

> 说明：`total count` 可在应用启动时查询一次并缓存（数据只读，不会变化），后续随机查询仅需一次 rowid 定位，响应时间 < 1ms。

**FTS5 查询实现：**

```sql
-- FTS5 全文搜索（支持中文 unicode61 分词）
SELECT f.poem_id, f.title, f.author,
       SUBSTR(f.content, 1, 80) AS summary,
       rank
FROM poem_fts f
WHERE poem_fts MATCH @searchQuery
ORDER BY rank
LIMIT @pageSize OFFSET @offset;

-- 总数查询
SELECT COUNT(*) AS total
FROM poem_fts f
WHERE poem_fts MATCH @searchQuery;
```

**搜索关键词处理逻辑（业务层）：**

```javascript
// 1. 对用户输入进行 FTS5 查询格式化
function buildFtsQuery(keyword) {
  // 转义 FTS5 特殊字符
  const escaped = keyword.replace(/['"(){}*]/g, '');
  // 使用双引号包裹，做前缀匹配
  return `"${escaped}"`;
}

// 2. matchField 判定逻辑
// 搜索完成后，检查匹配来源：
// - 若 title 包含关键词 → matchField = "title"
// - 若 author 包含关键词 → matchField = "author"
// - 否则 → matchField = "content"
// 排序优先级：title 匹配 > author 匹配 > content 匹配
```

**排序优先级实现：**

```sql
-- 使用 UNION ALL 分优先级查询
SELECT *, 1 AS priority FROM (
    SELECT f.poem_id, f.title, f.author, ...
    FROM poem_fts f WHERE f.title MATCH @query
) UNION ALL
SELECT *, 2 AS priority FROM (
    SELECT f.poem_id, f.title, f.author, ...
    FROM poem_fts f WHERE f.author MATCH @query AND f.title NOT MATCH @query
) UNION ALL
SELECT *, 3 AS priority FROM (
    SELECT f.poem_id, f.title, f.author, ...
    FROM poem_fts f WHERE f.content MATCH @query
      AND f.title NOT MATCH @query AND f.author NOT MATCH @query
)
ORDER BY priority
LIMIT @pageSize OFFSET @offset;
```

> 简化方案：若上述 UNION 查询性能不佳，可改用单次 FTS5 查询 + 业务层排序（按 priority 字段），在 78,000 条记录下 FTS5 查询本身 < 200ms，业务层排序开销可忽略。

## 九、风险与缓解

### 9.1 已有风险（来自总体方案）

#### R1：chinese-poetry 数据集格式不统一或字段缺失

| 项目 | 内容 |
|---|---|
| 等级 | 中 |
| 影响 | 数据导入失败或部分记录丢失 |
| 缓解措施 | (1) 数据清洗脚本 `data-cleaner.js` 实现健壮的字段映射，兼容 `title`/`rhythmic`、`content`/`paragraphs` 两套命名；(2) 过滤规则宽容处理——仅跳过标题+正文均为空的记录；(3) 导入报告输出跳过/失败明细，便于排查；(4) 测试阶段抽检 100 条记录验证字段完整性 |
| 验证方式 | `npm run init-data` 输出成功数 >= 10,000 |

#### R2：SQLite 在大数据量下搜索性能不达标

| 项目 | 内容 |
|---|---|
| 等级 | 低 |
| 影响 | 搜索响应 > 500ms，不满足 AC3 |
| 缓解措施 | (1) 优先使用 FTS5 全文搜索索引，避免 LIKE '%keyword%' 全表扫描；(2) 为 poems 表筛选字段（author_id、dynasty_id、category）建立 B-Tree 索引；(3) 搜索结果分页，每次仅返回 20 条；(4) 若 FTS5 仍不达标，可限制搜索范围（如仅搜索标题+作者） |
| 验证方式 | 使用 10 个典型关键词测试，记录响应时间均 <= 500ms |

#### R3：古典风格 UI 设计耗时超预期

| 项目 | 内容 |
|---|---|
| 等级 | 低 |
| 影响 | 界面不够美观，但不影响功能 |
| 缓解措施 | (1) 本文档 7.4 节已定义完整配色方案、字体选择、CSS 变量，开发时直接引用；(2) 优先实现功能逻辑，样式从基础版开始，有时间再迭代；(3) 使用 CSS 变量集中管理样式，调整配色只需修改变量文件 |
| 验证方式 | AC6 人工评审 |

#### R4：数据集体积过大导致导入或仓库管理困难

| 项目 | 内容 |
|---|---|
| 等级 | 低 |
| 影响 | 开发环境磁盘占用大，Git 仓库膨胀 |
| 缓解措施 | (1) 仅导入唐诗 + 宋词核心数据，不导入全量（元曲、全元曲等）；(2) 使用 `git clone --depth 1` 浅克隆减少下载量；(3) `data/` 目录加入 `.gitignore`，不纳入版本管理；(4) 导入脚本支持幂等执行，可删除 `data/` 后重新初始化 |
| 验证方式 | 确认 `data/` 不在 Git 跟踪中 |

### 9.2 新增风险

#### R5：better-sqlite3 原生编译问题

| 项目 | 内容 |
|---|---|
| 等级 | 低 |
| 影响 | `npm install` 阶段编译原生模块失败 |
| 缓解措施 | (1) 在 AGENT.md 中明确 Node.js >= 18 版本要求；(2) better-sqlite3 提供预编译二进制，大多数平台无需本地编译；(3) 若遇编译问题，文档中提供 `npm rebuild better-sqlite3` 修复命令；(4) 备选方案：若目标环境无法编译，可切换为 sql.js（纯 JS 实现的 SQLite） |
