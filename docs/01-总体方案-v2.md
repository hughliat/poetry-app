## 一、项目背景与目标

### 1.1 背景

一期 MVP 已交付并稳定运行：收录 314,629 首诗词、13,887 位作者，搜索响应时间 14ms（远优于 500ms 目标），浏览/搜索/详情/随机推荐四项核心功能全部上线，8/8 验收标准达成。然而一期在用户体验层面仍有明显短板——不支持繁简切换、搜索高亮存在缺陷（前端未使用后端返回的 `originalKeyword`）、仅适配桌面与平板（>= 768px）而无手机适配、无收藏等个性化功能、缺少自动化测试保障回归质量。

### 1.2 一句话目标

在一期核心功能基础上，围绕"好用易用"原则，通过繁简切换、搜索体验优化、移动端适配、轻量收藏和自动化测试五项建设，将诗词应用从"能用"提升到"好用"。

### 1.3 与一期的关系

| 维度 | 一期 | 二期 |
|---|---|---|
| 核心定位 | 功能可用（MVP） | 体验提升（好用易用） |
| 功能范围 | F1-F4（浏览/搜索/详情/随机） | F5-F9（繁简切换/搜索优化/移动端/收藏/测试） |
| 技术栈 | Vue 3 + Vite + Express + SQLite | 不变，增量引入 Vitest + Supertest |
| 数据库 | 新建 4 张表 | 不新增表，无 Schema 变更 |
| 验收标准 | AC1-AC8 | AC9-AC14（叠加，不替代） |

### 1.4 成功标准

| 维度 | 标准 | 度量方式 |
|---|---|---|
| 繁简切换 | 一键切换，全文即时变化，响应 < 200ms | 人工操作 + 计时 |
| 搜索质量 | 高亮正确，简体搜索使用 originalKeyword | 10 组关键词测试 |
| 移动端 | 375px 宽度下核心页面布局正常 | Chrome DevTools 模拟验证 |
| 收藏功能 | 收藏/取消/列表/持久化四项可用 | 人工操作 + 刷新验证 |
| 测试覆盖 | 7 个 API 全部有自动化用例 | `npm test` 执行通过 |
| 回归无破坏 | 一期功能全部正常 | 回归测试 |

## 四、技术路线

### 4.1 繁简切换方案选型

**方案对比：**

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 前端本地转换 | 前端引入 opencc-js，在浏览器端完成繁简转换 | 零网络延迟，切换响应 < 200ms；不增加后端负载 | 前端包体积增加约 300KB（Converter 字典） |
| B. 后端 API 转换 | 新增 `/api/convert` 接口，后端转换后返回 | 前端零负担 | 每次切换需网络请求，响应受网络影响；314K 诗词全量转换不现实 |
| C. 数据库双存储 | 导入时同时存储简体和繁体两份数据 | 查询无需转换 | 数据库体积翻倍（304MB → 600MB+），导入时间大幅增加 |

**决策：采用方案 A（前端本地转换）。**

理由：
1. 后端已引入 opencc-js（搜索繁简转换），前端复用同一库，技术一致性好
2. 诗词详情页和搜索结果页的数据量有限（单首诗词或分页列表），前端转换耗时极低
3. 切换操作纯前端完成，响应 < 200ms 的验收标准轻松达成
4. 不增加数据库负担，不影响后端性能

**实现要点：**
- 前端新增 `src/client/utils/converter.js`，封装 opencc-js 的简体/繁体转换函数
- 新增 `src/client/composables/useScriptMode.js`（Vue 组合式函数），管理当前繁简状态
- 状态通过 `sessionStorage` 持久化（会话级别），切换后即时生效
- 在导航栏（`nav-bar.vue`）新增繁简切换按钮
- 诗词详情页（`poem-detail-view.vue`）、搜索结果页（`search-view.vue`）、诗词卡片（`poem-card.vue`）、首页随机卡片（`random-card.vue`）均需响应繁简状态

### 4.2 移动端适配方案

**现状分析：**

一期 CSS 体系基于 4 层全局样式文件：
- `variables.css`：CSS 变量（配色/字体/间距/圆角/阴影/布局）
- `reset.css`：浏览器样式重置
- `base.css`：基础排版（容器/标题/按钮/高亮）
- `responsive.css`：媒体查询（桌面 >= 1024px / 平板 768~1023px / 手机 < 768px）

一期 `responsive.css` 已有 `< 768px` 的基础手机适配（导航栏紧凑化、隐藏导航栏搜索框、详情页字号缩小），但不够完整——缺少 375px 极窄屏幕的专门处理，部分组件（筛选面板、诗词网格、分页器）在小屏下仍有溢出风险。

**断点设计（二期扩展）：**

| 断点名称 | 范围 | 目标设备 | 布局策略 |
|---|---|---|---|
| desktop | >= 1024px | 桌面显示器 | 双栏/多列网格，完整导航 |
| tablet | 768px ~ 1023px | 平板 | 单栏 + 折叠筛选，双列网格 |
| mobile | 375px ~ 767px | 大手机 / 小平板 | 单栏单列，汉堡菜单，底部搜索入口 |
| mobile-sm | < 375px | 小屏手机（兼容） | 与 mobile 一致，进一步缩减间距 |

**实现要点：**
- 扩展 `responsive.css`，新增 `@media (max-width: 767px)` 完善规则和 `@media (max-width: 374px)` 补充规则
- 导航栏：手机端改为汉堡菜单 + 独立搜索页入口，繁简切换按钮保留在导航栏
- 诗词网格（`.poem-grid`）：手机端强制单列
- 筛选面板（`.filter-panel`）：手机端折叠为可展开面板
- 分页器（`.pagination`）：手机端缩减页码显示数量
- 详情页（`.detail-content`）：手机端正文行距适当缩小，保证单行不溢出
- 收藏列表页：新增页面，直接采用移动优先设计
- 所有间距使用 CSS 变量（`--spacing-*`），通过媒体查询调整变量值实现全局适配

### 4.3 收藏存储方案

**决策：使用 localStorage，不引入数据库。**

理由：
1. 收藏是轻量个性化功能，无需跨设备同步
2. 避免引入用户注册/登录系统的复杂度
3. localStorage 读写简单，API 成熟，浏览器兼容性好
4. 收藏数据量极小（每条记录约 100 字节），5MB 限制可存储约 50,000 条，远超个人使用需求

**localStorage 数据结构设计：**

```json
{
  "poetry_favorites": {
    "version": 1,
    "items": [
      {
        "id": "tang-001",
        "title": "静夜思",
        "author": "李白",
        "dynasty": "唐",
        "category": "五言绝句",
        "addedAt": "2026-10-01T12:00:00.000Z"
      }
    ]
  }
}
```

**设计要点：**
- 使用统一 key `poetry_favorites`，避免与其他应用冲突
- `version` 字段预留数据结构升级能力
- 每条记录存储最小必要字段（id + 展示所需字段 + 收藏时间），不存储完整诗词正文
- 按 `addedAt` 降序排列（最近收藏的在前）
- 新增 `src/client/composables/useFavorites.js` 封装收藏的增删查改逻辑
- 新增 `src/client/utils/storage.js` 封装 localStorage 读写，含异常处理（配额溢出等）

### 4.4 测试框架选型

**决策：Vitest（单元测试 + 集成测试） + Supertest（API 端到端测试）。**

理由：
1. Vitest 与 Vite 生态天然兼容，配置简单，无需额外 Babel 配置
2. Supertest 是 Node.js API 测试的事实标准，与 Express 配合良好
3. 一期后端三层架构（路由/业务/数据访问）适合分层测试
4. 后端已使用 ESM（`"type": "module"`），Vitest 原生支持 ESM

**测试范围规划：**

| 层级 | 测试对象 | 框架 | 用例数（预估） |
|---|---|---|---|
| API 集成测试 | 7 个 REST 端点的正常与异常响应 | Vitest + Supertest | ~35 个 |
| 业务逻辑测试 | poem-service 的搜索/分页/繁简转换 | Vitest | ~15 个 |
| 前端组件测试 | 核心组件渲染与交互（可选） | Vitest + @vue/test-utils | 视时间 |

**7 个 API 测试场景概要：**

| API | 正常场景 | 异常场景 |
|---|---|---|
| GET /api/poems | 默认分页、指定页码、按朝代筛选、按作者筛选 | 页码越界返回空列表、非法 pageSize |
| GET /api/poems/:id | 存在的 ID 返回详情 | 不存在的 ID 返回 404 |
| GET /api/poems/random | 返回随机诗词，连续调用不完全相同 | — |
| GET /api/poems/search?q= | 关键词匹配、繁简搜索、分页、返回 originalKeyword | 空关键词返回空列表、特殊字符不报错 |
| GET /api/authors | 默认列表、按朝代筛选 | 非法朝代参数返回空列表 |
| GET /api/dynasties | 返回完整朝代列表 | — |
| GET /api/categories | 返回分类列表 | — |

### 4.5 新增 API 规划

二期 **不新增后端 API**。理由：
1. 繁简切换：前端本地完成，无需后端参与
2. 搜索优化：后端已返回 `originalKeyword`，仅需前端修复使用方式
3. 收藏功能：纯前端 localStorage，不涉及后端
4. 移动端适配：纯 CSS 变更
5. 自动化测试：测试现有 API，不新增

此设计确保二期改动对后端零侵入，降低回归风险（AC14）。

### F6：搜索体验优化（P0）

**功能描述：** 修复一期遗留的搜索高亮缺陷，优化搜索结果展示体验。

**问题根因：**
- 后端 `searchPoems` 已返回 `originalKeyword`（用户原始输入），但前端 `search-view.vue` 将 `keyword`（route.query.q）传给 `poem-card` 做高亮
- 当数据库内容为繁体而用户输入简体时，前端用简体关键词在繁体文本中做正则匹配，导致高亮失败

**修复方案：**
- 前端 `search-view.vue` 从 API 响应中取出 `originalKeyword`，传递给 `poem-card` 的 `highlightKeyword` prop
- `poem-card.vue` 的高亮逻辑同时支持原始关键词和繁简匹配：先用 `originalKeyword` 尝试高亮，若不匹配则尝试转换后的高亮
- 搜索结果页增加"搜索模式"提示（如"已自动转换为繁体搜索"），提升用户感知

**影响范围：**
- 修改文件：`search-view.vue`（传递 originalKeyword）、`poem-card.vue`（高亮逻辑增强）

**验收关联：** AC10

**验收关联：** AC13

## 七、非功能需求

### 7.1 性能

| 指标 | 要求 | 说明 |
|---|---|---|
| 繁简切换响应时间 | <= 200ms | 前端本地转换，不含网络请求 |
| 搜索响应时间 | <= 500ms | 与一期一致，二期不引入后端性能退化 |
| 收藏操作响应 | <= 50ms | localStorage 读写，即时反馈 |
| 首屏加载时间 | <= 2s | 前端新增 opencc-js 字典约 300KB，需通过代码分割控制影响 |
| 测试执行时间 | <= 30s | 全部自动化测试用例执行完毕 |

### 7.2 可用性

| 指标 | 要求 |
|---|---|
| 繁简切换 | 切换按钮始终可见（导航栏），操作无歧义，状态可感知 |
| 搜索高亮 | 高亮颜色与古典风格协调，不遮挡正文阅读 |
| 移动端体验 | 触控友好（按钮 >= 44px 触控区域），无横向滚动条，文字可读 |
| 收藏反馈 | 收藏/取消操作有即时的视觉反馈（按钮状态变化） |
| 错误处理 | localStorage 不可用时（隐私模式/配额溢出）给出友好提示 |

### 7.3 兼容性

| 维度 | 要求 |
|---|---|
| 浏览器 | Chrome >= 90、Firefox >= 90、Safari >= 15、Edge >= 90（与一期一致） |
| 移动端浏览器 | iOS Safari >= 15、Android Chrome >= 90、微信内置浏览器 |
| 设备宽度 | >= 375px（iPhone SE 及以上） |
| localStorage | 需支持 localStorage（不支持的环境收藏功能降级并提示） |

### 7.4 可维护性

| 维度 | 要求 |
|---|---|
| 代码规范 | ESLint 检查零 error（与一期一致） |
| 繁简转换模块 | 封装为独立 utils，便于后续替换或升级 |
| 收藏模块 | composable + storage 分层，业务逻辑与存储解耦 |
| 测试可维护性 | 测试用例按 API 分组，命名清晰，断言明确 |
| CSS 变量体系 | 移动端适配通过调整变量值实现，不引入新的样式方案 |
