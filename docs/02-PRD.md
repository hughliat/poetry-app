## 二、产品概述

### 2.1 一句话目标

构建一个轻量级的诗词阅读与搜索 Web 应用，让用户可以浏览、检索中国古典诗词（唐诗宋词为主），获得沉浸式阅读体验。

### 2.2 目标用户

| 画像 | 描述 | 核心诉求 |
|---|---|---|
| 诗词爱好者（主要） | 对中国古典诗词有兴趣，日常阅读欣赏 | 快速找到某首诗或某位作者的作品 |
| 学生/教师（次要） | 学习或教学中需要查阅诗词 | 按关键词或作者检索特定内容 |
| 文化探索者（次要） | 对诗词不太熟悉，希望发现新作品 | 通过随机推荐培养兴趣 |

## 三、需求列表

### 3.1 P0 需求（MVP 必须实现）

本期共 4 条 P0 需求，对应总体方案核心功能 F1 ~ F4。

#### 需求编号：REQ-001
- **需求名称**：诗词浏览
- **优先级**：P0
- **描述**：作为诗词爱好者，我希望按朝代、作者、诗体/词牌分类浏览诗词列表，以便系统性地阅读和发现作品。
- **验收标准**（给定-当-那么格式）：
  - 给定 用户已进入浏览页
  - 当 用户选择某个朝代（如"唐"）进行筛选
  - 那么 系统展示该朝代下所有诗词列表，每页 20 条，分页功能正常
  - 给定 用户已选择某位作者（如"李白"）
  - 当 用户浏览该作者的作品列表
  - 那么 系统仅展示该作者的全部诗词，列表按标题排序
- **关联功能**：F1

#### 需求编号：REQ-002
- **需求名称**：关键词搜索
- **优先级**：P0
- **描述**：作为学生/教师，我希望在诗词标题、作者、正文中进行关键词搜索，以便快速定位包含特定内容的诗词。
- **验收标准**（给定-当-那么格式）：
  - 给定 用户在搜索框中输入关键词（如"月"）
  - 当 用户提交搜索请求
  - 那么 系统返回标题、作者或正文中包含该关键词的诗词列表，响应时间 <= 500ms
  - 给定 用户输入关键词后搜索无匹配结果
  - 当 系统完成检索
  - 那么 系统展示"未找到相关诗词"的友好提示信息
- **关联功能**：F2

#### 需求编号：REQ-003
- **需求名称**：诗词详情
- **优先级**：P0
- **描述**：作为诗词爱好者，我希望查看单首诗词的完整信息（标题、作者、朝代、正文），以便获得沉浸式阅读体验。
- **验收标准**（给定-当-那么格式）：
  - 给定 用户在浏览列表或搜索结果中看到一首诗词
  - 当 用户点击该诗词条目
  - 那么 系统跳转至详情页，完整展示标题、作者、朝代、正文内容，排版清晰可读
  - 给定 用户在诗词详情页
  - 当 页面加载完成
  - 那么 所有字段（标题、作者、朝代、正文）均正确显示，无缺失或乱码
- **关联功能**：F3

#### 需求编号：REQ-004
- **需求名称**：随机推荐
- **优先级**：P0
- **描述**：作为文化探索者，我希望系统随机推荐一首诗词，并支持"换一首"操作，以便发现未曾阅读的作品。
- **验收标准**（给定-当-那么格式）：
  - 给定 用户点击"随机推荐"按钮
  - 当 系统响应请求
  - 那么 系统从数据库中随机选取一首诗词并展示其完整信息

  - 当 系统每次返回一首诗词
  - 那么 5 次结果中至少有 2 首不同的诗词（不完全重复）
- **关联功能**：F4

## 四、功能需求详述

### 4.1 REQ-001 诗词浏览

#### 功能说明

用户可通过朝代、作者、诗体/词牌等维度分类浏览诗词列表。浏览页是应用的核心导航入口，帮助用户系统性地发现诗词作品。

#### 交互流程

1. 用户从首页或导航栏进入浏览页（`/browse`）
2. 页面默认展示全部诗词列表（按朝代分组或按标题排序）
3. 用户通过筛选区域选择筛选条件：
   - 选择朝代（如"唐"、"宋"）
   - 选择作者（如"李白"、"苏轼"）
   - 选择诗体/词牌（如"五言绝句"、"水调歌头"）
4. 系统根据筛选条件刷新诗词列表
5. 列表支持分页，每页 20 条，用户可翻页或跳转至指定页
6. 用户点击某条诗词标题，跳转至详情页（`/poem/:id`）

#### 界面要素

| 元素 | 说明 |
|---|---|
| 筛选面板 | 位于页面左侧或顶部，包含朝代下拉选择、作者搜索/选择、诗体/词牌选择 |
| 诗词列表 | 卡片或列表形式展示，每条显示标题、作者、朝代、正文摘要（前两句） |
| 分页控件 | 位于列表底部，显示当前页码、总页数，支持上一页/下一页/跳转 |
| 排序选项 | 默认按标题排序，可扩展为按作者、朝代排序 |
| 空状态提示 | 筛选无结果时展示"该分类下暂无诗词"提示 |

#### 业务规则

- **分页规则**：每页固定 20 条记录；页码从 1 开始；当结果为空时展示空状态
- **筛选规则**：支持单一维度筛选（仅按朝代或仅按作者）；筛选条件可组合（朝代 + 作者）
- **排序规则**：默认按标题拼音排序；同一作者作品按标题排序
- **数据加载**：采用分页请求后端接口，每次仅加载当前页数据，避免一次性加载全量

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| 筛选条件无匹配结果 | 展示"该分类下暂无诗词，请尝试其他筛选条件" |
| 数据加载失败（网络/后端异常） | 展示"数据加载失败，请稍后重试"，提供重试按钮 |
| 翻页超出范围 | 禁用"下一页"按钮（最后一页）或"上一页"按钮（第一页） |

### 4.2 REQ-002 关键词搜索

#### 功能说明

用户可在搜索框中输入关键词，系统在诗词标题、作者、正文中进行模糊搜索，返回匹配结果列表。搜索基于 SQLite FTS5 全文索引实现，保证响应速度。

#### 交互流程

1. 用户在页面顶部搜索框中输入关键词（如"月"、"李白"、"静夜思"）
2. 用户按下回车键或点击搜索按钮
3. 系统跳转至搜索结果页（`/search?q=xxx`），展示匹配结果列表
4. 搜索结果按相关度排序（标题匹配优先，其次作者匹配，最后正文匹配）
5. 用户可点击搜索结果跳转至详情页
6. 搜索结果支持分页，每页 20 条

#### 界面要素

| 元素 | 说明 |
|---|---|
| 搜索框 | 位于页面顶部导航栏，支持输入关键词，带 placeholder 提示"搜索诗词标题、作者或内容" |
| 搜索结果列表 | 展示匹配的诗词条目，每条显示标题、作者、朝代、匹配内容摘要（关键词高亮） |
| 结果统计 | 显示"共找到 X 条结果" |
| 分页控件 | 与浏览页一致 |
| 空结果提示 | 搜索无匹配时展示"未找到与'XXX'相关的诗词，请尝试其他关键词" |
| 关键词高亮 | 搜索结果中匹配的关键词以高亮样式标注 |

#### 业务规则

- **搜索范围**：同时搜索标题（title）、作者（author）、正文（content）三个字段
- **匹配规则**：模糊匹配（LIKE 或 FTS5 全文搜索），支持中文关键词
- **排序规则**：标题匹配 > 作者匹配 > 正文匹配（按相关度优先级排序）
- **性能要求**：搜索响应时间 <= 500ms（本地 SQLite + FTS5 索引）
- **分页规则**：每页 20 条，与浏览页一致
- **输入规则**：搜索关键词不做长度限制，但空字符串不触发搜索

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| 搜索无结果 | 展示友好提示"未找到与'XXX'相关的诗词"，建议尝试其他关键词 |
| 搜索响应超时（> 500ms） | 展示"搜索耗时较长，请尝试缩短关键词" |
| 后端异常 | 展示"搜索服务暂时不可用，请稍后重试" |
| 特殊字符输入 | 正常处理，不对特殊字符做转义报错 |

### 4.3 REQ-003 诗词详情

#### 功能说明

用户点击诗词条目后进入详情页，展示该诗词的完整信息，包括标题、作者、朝代、正文内容。详情页追求排版美观、阅读舒适，体现古典风格。

#### 交互流程

1. 用户在浏览列表或搜索结果中点击某首诗词
2. 系统跳转至详情页（`/poem/:id`），URL 中包含诗词 ID
3. 页面加载并展示诗词完整信息
4. 用户可阅读完整诗词内容
5. 用户可通过页面内的链接/按钮返回浏览页或搜索结果

#### 界面要素

| 元素 | 说明 |
|---|---|
| 标题 | 诗词标题，居中展示，使用较大字号 |
| 作者信息 | 显示"[朝代] 作者名"，如"[唐] 李白"，位于标题下方 |
| 正文内容 | 诗词正文，按原始分行展示，使用衬线字体，行间距适当 |
| 分类标签 | 显示诗体/词牌分类（如有） |
| 返回按钮 | 返回上一页（浏览页或搜索结果页） |
| 注释区域 | 如数据中包含注释信息，在正文下方展示（可选区域） |

#### 业务规则

- **内容展示**：正文按原始分行展示，每行以换行分隔；诗词数组拼接为完整文本
- **字段完整性**：标题、作者、朝代、正文为必填展示字段；注释为可选字段
- **URL 规则**：详情页 URL 格式为 `/poem/:id`，id 为诗词在数据库中的唯一标识
- **数据加载**：通过后端 API 获取单首诗词完整数据

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| 诗词 ID 不存在 | 展示"未找到该诗词"的 404 页面，提供返回首页链接 |
| 数据加载失败 | 展示"内容加载失败，请稍后重试"，提供重试按钮 |
| 正文字段为空 | 展示"该诗词内容暂缺"提示 |
| 作者/朝代信息缺失 | 对应字段显示"未知" |

### 4.4 REQ-004 随机推荐

#### 功能说明

系统从数据库中随机选取一首诗词展示给用户，支持"换一首"操作重新随机获取。该功能帮助用户发现未曾阅读的作品，适合文化探索者使用。

#### 交互流程

1. 用户在首页点击"随机推荐"按钮
2. 系统从数据库中随机选取一首诗词
3. 页面展示该诗词的完整信息（标题、作者、朝代、正文）
4. 用户点击"换一首"按钮
5. 系统重新随机选取一首诗词并刷新展示
6. 用户可点击诗词标题跳转至详情页查看更多信息

#### 界面要素

| 元素 | 说明 |
|---|---|
| 随机推荐卡片 | 居中展示，包含诗词标题、作者、朝代、正文摘要 |
| "随机推荐"按钮 | 首页显著位置，触发首次随机推荐 |
| "换一首"按钮 | 在推荐卡片内或下方，点击后刷新推荐内容 |
| "查看详情"链接 | 跳转至当前推荐诗词的详情页 |
| 加载指示 | 切换诗词时短暂加载动画 |

#### 业务规则

- **随机逻辑**：使用数据库层面的随机查询（如 SQLite 的 `ORDER BY RANDOM() LIMIT 1`），确保全量数据等概率被选中
- **去重逻辑**：客户端记录最近展示的诗词 ID（至少记录最近 5 个），尽量避免连续重复；若数据库诗词总量充足（>= 1 万），连续 5 次不完全重复
- **展示规则**：推荐卡片展示标题、作者、朝代、正文前 2 行摘要；用户可点击查看详情
- **性能要求**：随机查询响应时间 <= 200ms

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| 数据库为空或无有效数据 | 展示"暂无诗词数据，请先执行数据初始化"提示 |
| 随机查询失败 | 展示"推荐服务暂时不可用，请稍后重试" |
| 连续多次返回相同诗词 | 正常现象（概率极低），不做特殊处理 |

## 六、数据需求

### 6.1 数据规模要求

- MVP 目标导入量：**>= 10,000 首诗词**
- 优先导入唐诗（约 57,000 首）和宋词（约 21,000 首）的核心数据
- 实际导入量预计远超最低要求，但验收标准为 >= 1 万首

### 6.2 数据来源

- **数据源**：[chinese-poetry](https://github.com/chinese-poetry/chinese-poetry) 开源数据集
- **协议**：CC0/公有领域，可自由使用
- **数据格式**：JSON 文件，按朝代/类别组织目录
- **主要导入目录**：`唐诗/`、`宋词/`

### 6.3 数据质量要求

| 维度 | 要求 |
|---|---|
| 字段完整性 | 每条记录必须包含：标题（title）、作者（author）、朝代（dynasty）、正文（content）；注释（annotation）为可选字段 |
| 去重规则 | 按 title + author 组合判断重复，重复记录仅保留一条 |
| 有效性 | 过滤空内容（正文为空或标题为空的记录）；过滤无效数据（字段缺失严重的条目） |
| 字段统一 | 唐诗字段（title/content）与宋词字段（rhythmic/paragraphs）在导入时统一为相同命名 |
| 编码要求 | 统一使用 UTF-8 编码，确保中文内容无乱码 |
| 导入验证 | 导入完成后输出统计信息（成功数、跳过数、失败数），并验证总记录数 >= 10,000 |

## 九、排他说明

### 9.1 本期不做的功能

以下功能明确不纳入本期 MVP 范围，与总体方案 2.2 节保持一致：

| 排除项 | 原因 |
|---|---|
| 用户系统（注册/登录/收藏） | MVP 聚焦阅读与搜索核心功能，用户系统增加开发复杂度，属二期范围 |
| AI 生成（诗词赏析/配图） | 技术复杂度高，需要额外 AI 服务集成，非核心阅读需求 |
| 社区互动（评论/分享/讨论） | 依赖用户系统前置，且非 MVP 阅读场景的核心诉求 |
| 公网部署 | MVP 阶段本地运行演示即可，不投入服务器成本和运维成本 |
| 诗词背诵/默写功能 | 教育类需求，与 MVP 定位的阅读/搜索场景不同 |
| 多语言/繁体切换 | 数据源为简体中文，繁体转换需额外数据映射，二期可扩展 |

### 9.2 不做的原因总结

1. **聚焦核心价值**：MVP 的目标是验证"诗词阅读 + 搜索"这一核心场景，上述排除项均不属于该核心
2. **控制开发成本**：用户系统、AI 集成、社区功能均显著增加开发工作量
3. **避免范围蔓延**：明确排除项可防止开发过程中需求不断膨胀
4. **降低技术风险**：公网部署、AI 服务集成引入额外技术依赖和运维复杂度
5. **二期可平滑扩展**：上述功能已在 P2 需求中记录，二期可基于 MVP 架构逐步扩展
