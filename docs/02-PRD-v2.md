## 二、产品概述

### 2.1 一句话目标

在一期核心功能（浏览/搜索/详情/随机推荐）稳定运行的基础上，围绕"好用易用"原则，通过繁简切换、搜索体验优化、移动端适配、轻量收藏和自动化测试五项建设，将诗词应用从"能用"提升到"好用"。

### 2.2 目标用户

延续一期用户画像，补充二期新增关注点：

| 画像 | 描述 | 二期新增关注点 |
|---|---|---|
| 诗词爱好者（主要） | 对中国古典诗词有兴趣，日常阅读欣赏 | 习惯阅读繁体版本，需要在手机上随时浏览 |
| 学生/教师（次要） | 学习或教学中需要查阅诗词，按关键词或作者检索 | 搜索高亮需准确，方便快速定位关键词在正文中的位置 |
| 文化探索者（次要） | 对诗词不太熟悉，希望通过随机推荐发现新作品 | 遇到喜欢的诗想收藏起来，方便以后回顾 |

### 3.1 P0 需求（二期必须实现）

## 四、功能需求详述

### 4.1 REQ-010 繁简切换

#### 功能说明

在导航栏新增繁简切换按钮，用户可一键切换全站诗词的显示字体（简体/繁体）。切换基于前端本地 opencc-js 库实现，无需网络请求，切换后标题、作者、正文即时变化。切换状态通过 sessionStorage 持久化，刷新页面后保持。

#### 交互流程

1. 用户在导航栏右侧看到繁简切换按钮，默认显示"繁"文字（表示当前为简体模式，点击可切换为繁体）
2. 用户点击切换按钮
3. 系统在 200ms 内完成全站文本转换：
   - 诗词标题由简体转为繁体（或反向）
   - 作者姓名由简体转为繁体（或反向）
   - 诗词正文由简体转为繁体（或反向）
4. 切换按钮文字更新为"简"（表示当前为繁体模式，点击可切换回简体）
5. 切换状态写入 sessionStorage，用户刷新页面后保持当前模式
6. 用户在繁体模式下浏览不同页面（浏览页、搜索页、详情页、收藏页），所有页面均保持繁体显示
7. 用户再次点击切换按钮，全站恢复简体显示

#### 界面要素

| 元素 | 说明 |
|---|---|
| 繁简切换按钮 | 位于导航栏右侧，与收藏入口并列。按钮为文字按钮，显示当前可切换的目标模式（简体模式下显示"繁"，繁体模式下显示"简"）。按钮尺寸不小于 44px x 44px（移动端触控友好） |
| 诗词标题文本 | 诗词详情页、搜索结果页、浏览列表、收藏列表中的标题文本，均响应繁简切换 |
| 作者姓名文本 | 所有展示作者姓名的位置，均响应繁简切换 |
| 诗词正文文本 | 诗词详情页的正文内容、搜索结果中正文摘要、诗词卡片中的正文摘要，均响应繁简切换 |
| 加载指示 | 切换操作为即时完成，无需加载指示；首次加载 opencc-js 字典时可有短暂过渡（通过 Vite 动态导入优化） |

#### 业务规则

- **转换范围**：仅转换诗词内容相关文本（标题、作者、正文），不转换 UI 控件文本（按钮、标签、提示信息等保持简体）
- **默认状态**：首次访问默认为简体模式（与一期行为一致）
- **状态持久化**：使用 sessionStorage 存储当前模式（`scriptMode: 'simplified' | 'traditional'`），会话级别保持。关闭浏览器标签页后重置为简体
- **转换引擎**：使用 opencc-js 的 `s2t`（简体转繁体）和 `t2s`（繁体转简体）转换器，前端本地执行
- **影响页面**：`poem-detail-view.vue`（详情页）、`search-view.vue`（搜索页）、`poem-card.vue`（诗词卡片）、`random-card.vue`（首页随机卡片）、`favorites-view.vue`（收藏页）
- **与搜索高亮的协调**：繁简切换后，搜索结果页的关键词高亮仍须正确。高亮逻辑需感知当前繁简模式，在对应模式下使用正确的关键词进行匹配

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| opencc-js 字典加载失败（网络异常/文件缺失） | 切换按钮点击后展示提示"字体转换服务加载失败，请稍后重试"，保持当前模式不变 |
| sessionStorage 不可用（隐私模式） | 繁简切换仍可使用，但刷新后恢复为默认简体模式。不阻断切换功能 |
| 切换后部分文本未转换 | 确保所有诗词相关文本节点均通过 composable 的响应式状态驱动，避免遗漏 |
| 繁简切换导致搜索高亮失效 | 切换后触发搜索结果重新渲染，高亮逻辑使用当前模式下的关键词进行匹配 |

### 4.2 REQ-011 搜索体验优化

#### 功能说明

修复一期遗留的搜索高亮缺陷：前端在渲染搜索结果时，未使用后端返回的 `originalKeyword` 字段，而是使用 `route.query.q`（可能被前端繁简转换污染的关键词）进行高亮匹配，导致简体关键词在繁体正文中无法正确高亮。二期修复该问题，同时优化搜索结果展示体验。

#### 交互流程

1. 用户在搜索框中输入简体关键词（如"月"），提交搜索
2. 后端接收请求，执行搜索，返回结果中包含 `originalKeyword: "月"` 字段
3. 前端 `search-view.vue` 从 API 响应中读取 `originalKeyword`，将其传递给 `poem-card` 组件的 `highlightKeyword` prop
4. `poem-card.vue` 使用 `highlightKeyword` 在正文摘要中进行高亮匹配：
   - 优先使用 `originalKeyword` 进行正则匹配
   - 若 `originalKeyword` 在正文中未匹配到（正文为繁体而关键词为简体），则将 `originalKeyword` 通过 opencc-js 转换为繁体后再尝试匹配
5. 匹配到的关键词以高亮样式（`<mark>` 标签或 CSS 高亮类）标注
6. 搜索结果页增加搜索模式提示：当后端对关键词进行了繁简转换时，显示"已自动匹配繁简体"的辅助提示

#### 界面要素

| 元素 | 说明 |
|---|---|
| 搜索结果高亮 | 搜索结果中匹配的关键词以高亮样式标注（背景色 `var(--color-highlight)` 或使用 `<mark>` 标签），高亮颜色与古典风格协调，不遮挡正文阅读 |
| 搜索模式提示 | 搜索结果列表上方，当后端执行了繁简自动转换时显示"已自动匹配繁简体"提示文字，使用辅助文字样式（较小字号、较浅颜色） |
| 结果统计 | 显示"共找到 X 条与'关键词'相关的结果"，关键词使用用户原始输入 |
| 空结果提示 | 搜索无匹配时展示"未找到与'关键词'相关的诗词，请尝试其他关键词"，关键词使用用户原始输入 |

#### 业务规则

- **高亮关键词来源**：必须使用后端 API 返回的 `originalKeyword` 字段，而非 `route.query.q`。`originalKeyword` 是用户搜索时输入的原始关键词，未经繁简转换
- **高亮匹配策略**：`poem-card.vue` 的高亮函数接收 `highlightKeyword` 参数，先在原始文本中匹配；若不匹配，尝试将关键词进行繁简转换后再匹配。确保简体关键词能高亮繁体正文中的对应字
- **高亮渲染方式**：使用安全的 HTML 渲染方式（如 Vue 的 `v-html` 配合 DOMPurify 消毒，或使用计算属性生成安全的 HTML 片段），防止 XSS 注入
- **搜索范围不变**：与一期一致，搜索范围覆盖标题、作者、正文三个字段
- **排序规则不变**：标题匹配 > 作者匹配 > 正文匹配

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| `originalKeyword` 字段缺失（后端异常） | 降级使用 `route.query.q` 进行高亮，保持与一期行为一致 |
| 关键词包含正则特殊字符（如 `.`、`*`、`(`） | 高亮函数中对关键词进行正则转义（escapeRegExp），避免正则解析错误 |
| 高亮后 HTML 结构被破坏 | 高亮替换仅在文本节点中进行，不替换 HTML 标签内的内容；使用安全的 HTML 拼接方式 |
| 用户输入空关键词 | 不触发搜索，保持当前页面状态 |
| 用户输入超长关键词（> 100 字符） | 正常传递给后端，由后端处理截断或返回空结果 |

### 4.3 REQ-012 移动端适配

#### 功能说明

在现有桌面（>= 1024px）和平板（768px ~ 1023px）适配基础上，新增 375px 手机断点（375px ~ 767px）和极窄屏兼容断点（< 375px），确保全部核心页面在手机屏幕上布局正常、触控友好。导航栏在移动端改为汉堡菜单模式，筛选面板折叠为可展开区域。

#### 交互流程

1. 用户使用手机（屏幕宽度 375px）访问应用
2. 导航栏自动切换为移动端模式：
   - 左侧显示应用 Logo/标题
   - 右侧显示汉堡菜单按钮（三横线图标）
   - 搜索入口通过汉堡菜单或独立搜索图标访问
   - 繁简切换按钮和收藏入口保留在导航栏可见位置
3. 用户点击汉堡菜单按钮，展开侧边抽屉菜单（或下拉菜单），显示导航链接：首页、浏览、搜索、收藏
4. 用户进入浏览页：
   - 筛选面板默认折叠，用户点击"筛选"按钮展开
   - 诗词列表为单列显示，每条卡片宽度 100%
   - 分页器紧凑显示，减少页码按钮数量
5. 用户进入搜索页：
   - 搜索框全宽显示
   - 搜索结果单列排列
   - 分页器紧凑显示
6. 用户进入诗词详情页：
   - 标题字号适当缩小，适配屏幕宽度
   - 正文行距适当缩减，保证内容完整显示
   - 返回按钮位于顶部易触达位置
   - 收藏按钮位于标题右侧，触控区域 >= 44px
7. 用户进入收藏页：
   - 列表单列显示
   - 空状态友好提示
8. 当屏幕宽度 < 375px（如 iPhone 4/5），间距进一步缩减，布局与 mobile 一致

#### 界面要素

| 元素 | 说明 |
|---|---|
| 汉堡菜单按钮 | 导航栏右侧，三横线图标，点击展开/收起导航菜单。触控区域 >= 44px x 44px |
| 侧边抽屉菜单 | 从右侧滑出，覆盖层展示导航链接（首页、浏览、搜索、收藏），点击遮罩层或链接后关闭 |
| 筛选展开按钮 | 浏览页顶部，文字按钮"筛选"或漏斗图标，点击展开/收起筛选面板 |
| 折叠筛选面板 | 展开后显示朝代、作者、分类筛选条件，默认收起状态 |
| 单列诗词卡片 | 浏览页和搜索页的诗词卡片，宽度 100%，间距使用 CSS 变量 `--spacing-sm` |
| 紧凑分页器 | 减少可见页码数量（如仅显示当前页前后各 1 页），按钮尺寸适当缩小 |
| 全宽搜索框 | 搜索页中搜索框宽度 100%，placeholder 提示搜索范围 |
| 自适应标题 | 详情页标题字号根据屏幕宽度自适应（使用 CSS `clamp()` 或媒体查询调整） |
| 触控友好按钮 | 所有可点击元素（收藏按钮、切换按钮、分页按钮）触控区域 >= 44px x 44px |

#### 业务规则

- **断点定义**：
  - `desktop`：>= 1024px，双栏/多列网格，完整导航（沿用一期）
  - `tablet`：768px ~ 1023px，单栏 + 折叠筛选，双列网格（沿用一期）
  - `mobile`：375px ~ 767px，单栏单列，汉堡菜单，筛选折叠（二期新增）
  - `mobile-sm`：< 375px，与 mobile 一致，进一步缩减间距（二期新增，兼容保障）
- **CSS 实现策略**：通过扩展 `responsive.css` 中的媒体查询规则实现，新增 `@media (max-width: 767px)` 和 `@media (max-width: 374px)` 规则段。所有间距通过 CSS 变量（`--spacing-*`）调整，不引入新的样式方案
- **导航栏重构策略**：采用渐进方式——先完成 CSS 布局适配，再处理汉堡菜单交互重构。确保每个阶段一期功能均可正常使用（AC14 回归保障）
- **诗词网格**：`.poem-grid` 在 mobile 断点下强制 `grid-template-columns: 1fr`（单列）
- **触控区域**：所有可交互元素最小触控区域 44px x 44px，符合 Apple HIG 和 Material Design 规范
- **无横向滚动**：`body` 设置 `overflow-x: hidden`，所有容器使用 `max-width: 100%` 和 `box-sizing: border-box`

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| 极窄屏幕（< 375px）下文字溢出 | 标题使用 `word-break: break-all` 或 `text-overflow: ellipsis` 处理超长标题；正文使用 `overflow-wrap: break-word` |
| 汉堡菜单展开时用户旋转屏幕 | 菜单保持展开状态，CSS 媒体查询自动调整布局，不出现错位 |
| 筛选面板展开状态下切换页面 | 筛选状态保持（通过 URL query 参数或组件状态），面板折叠状态重置 |
| 微信内置浏览器兼容问题 | 测试微信内置浏览器（基于 WebKit）下的布局表现，确保 CSS Grid/Flexbox 正常渲染 |
| 虚拟键盘弹出导致布局错乱 | 使用 `vh` 单位时考虑 `visualViewport` API 或使用 `100dvh`（dynamic viewport height） |

### 4.4 REQ-013 诗词收藏

#### 功能说明

用户在诗词详情页可一键收藏/取消收藏当前诗词，通过导航栏进入"我的收藏"页面查看所有已收藏诗词。收藏数据通过 localStorage 持久化存储，无需注册登录，刷新页面后数据不丢失。

#### 交互流程

1. 用户在诗词详情页浏览一首诗词
2. 用户点击标题右侧的收藏按钮（心形空心图标）
3. 收藏按钮即时变为已收藏状态（心形实心图标 + 文字"已收藏"），诗词信息保存至 localStorage
4. 用户通过导航栏的"收藏"入口进入收藏列表页（`/favorites`）
5. 收藏列表页展示所有已收藏诗词，每条显示标题、作者、朝代，按收藏时间倒序排列（最近收藏的在最前）
6. 用户点击收藏列表中的某条诗词，跳转至该诗词的详情页
7. 用户在收藏列表页可取消收藏：
   - 桌面端：点击诗词卡片上的取消收藏按钮（心形实心图标）
   - 移动端：左滑卡片露出"取消收藏"按钮，或长按卡片弹出操作菜单
8. 取消收藏后，该条目从列表中即时移除，列表自动刷新
9. 用户关闭浏览器后重新打开应用，进入收藏页，之前收藏的诗词仍然存在

#### 界面要素

| 元素 | 说明 |
|---|---|
| 收藏按钮（详情页） | 位于诗词详情页标题右侧，心形图标。未收藏时显示空心（`♡`），已收藏时显示实心（`♥`）+ 辅助文字"已收藏"。按钮触控区域 >= 44px x 44px |
| 收藏入口（导航栏） | 导航栏中显示"收藏"文字链接或心形图标，点击跳转至 `/favorites` 页面。在移动端汉堡菜单中也显示该入口 |
| 收藏列表页 | 新增页面，路由 `/favorites`。页面标题"我的收藏"，展示收藏诗词列表 |
| 收藏诗词卡片 | 收藏列表中的每条记录，显示标题、作者、朝代、收藏时间。点击跳转至详情页 |
| 空状态提示 | 当收藏列表为空时，显示"还没有收藏的诗词，去发现喜欢的作品吧"提示文字，附带"去浏览"按钮跳转至浏览页 |
| 取消收藏操作 | 桌面端：卡片右上角取消按钮。移动端：左滑露出"取消收藏"按钮，或长按弹出操作菜单 |

#### 业务规则

- **存储结构**：使用 localStorage，key 为 `poetry_favorites`，数据结构如下：
  ```json
  {
    "version": 1,
    "items": [
      {
        "id": "tang-001",
        "title": "静夜思",
        "author": "李白",
        "dynasty": "唐",
        "category": "五言绝句",
        "addedAt": "2026-10-01T12:00:00.000Z"
      }
    ]
  }
  ```
- **存储字段**：每条记录存储最小必要字段（id + 展示所需字段 + 收藏时间），不存储完整诗词正文，节省存储空间
- **排序规则**：按 `addedAt` 降序排列（最近收藏的在前）
- **去重规则**：以诗词 `id` 为唯一标识，同一首诗词不重复收藏。重复点击收藏按钮执行取消操作
- **容量评估**：每条记录约 100 字节，localStorage 5MB 限制可存储约 50,000 条，远超个人使用需求
- **收藏状态同步**：详情页的收藏按钮状态须与 localStorage 实时同步。用户在详情页收藏后，收藏列表页须即时反映；在收藏列表页取消收藏后，详情页的收藏按钮须同步更新
- **数据迁移**：`version` 字段预留数据结构升级能力。读取时检查 version，若不匹配当前版本则执行迁移逻辑
- **操作响应时间**：收藏/取消操作响应 <= 50ms（localStorage 读写 + UI 更新）

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| localStorage 不可用（隐私模式/无痕模式） | 收藏按钮置灰，点击时提示"当前浏览器不支持收藏功能"。不阻断其他功能使用 |
| localStorage 配额溢出（接近 5MB） | 提示"收藏空间已满，请取消部分收藏后重试"。提供快速清理入口 |
| localStorage 数据损坏（JSON 解析失败） | 捕获解析异常，清空损坏数据，提示"收藏数据异常，已重置"。降级为空收藏列表 |
| 收藏的诗词在数据库中已不存在 | 收藏列表中仍正常展示（收藏数据独立于后端数据库），点击跳转详情页时由详情页处理 404 逻辑 |
| 多标签页同时操作收藏 | 监听 `storage` 事件，当其他标签页修改收藏数据时，当前标签页自动同步更新 |

### 4.5 REQ-014 自动化测试

#### 功能说明

使用 Vitest + Supertest 为后端 7 个 REST API 编写自动化测试用例，覆盖正常场景与异常场景。测试文件按 API 分组组织，通过 `npm test` 一键执行全部测试。测试使用现有 poetry.db 数据库，为只读验证，不修改数据库内容。

#### 交互流程

1. 开发者在项目中执行 `npm test` 命令
2. Vitest 启动，加载 `src/server/tests/` 目录下的全部测试文件
3. 每个测试文件通过 Supertest 向后端 Express 应用发起 HTTP 请求
4. 测试用例验证响应状态码、响应体结构、响应数据内容
5. 全部测试通过后输出通过统计（如"Tests: 35 passed, 35 total"）
6. 若有测试失败，输出失败详情（失败用例名、期望值 vs 实际值）
7. 测试执行完毕，进程退出（`vitest run` 模式，非 watch 模式）

#### 界面要素

| 元素 | 说明 |
|---|---|
| 测试文件目录 | `src/server/tests/`，每个 API 一个测试文件 |
| `poems.test.js` | 覆盖 `GET /api/poems`：默认分页、指定页码、按朝代筛选、按作者筛选、页码越界返回空列表、非法 pageSize |
| `poem-detail.test.js` | 覆盖 `GET /api/poems/:id`：存在的 ID 返回详情、不存在的 ID 返回 404 |
| `poem-random.test.js` | 覆盖 `GET /api/poems/random`：返回随机诗词、连续调用不完全相同 |
| `poem-search.test.js` | 覆盖 `GET /api/poems/search`：关键词匹配、繁简搜索、分页、返回 originalKeyword、空关键词返回空列表、特殊字符不报错 |
| `authors.test.js` | 覆盖 `GET /api/authors`：默认列表、按朝代筛选、非法朝代参数返回空列表 |
| `dynasties.test.js` | 覆盖 `GET /api/dynasties`：返回完整朝代列表 |
| `categories.test.js` | 覆盖 `GET /api/categories`：返回分类列表 |
| npm test 脚本 | `package.json` 中配置 `"test": "vitest run"`，一键执行 |

#### 业务规则

- **测试框架**：Vitest（测试运行器 + 断言库）+ Supertest（HTTP 请求构造与响应断言）
- **测试组织**：按 API 分组，每个 API 一个独立测试文件，文件命名 `{api-name}.test.js`
- **测试数据策略**：使用项目已有的 `poetry.db`（开发环境数据库），测试为只读验证，不修改数据库内容，无数据准备/清理开销
- **测试环境**：测试直接引用 Express 应用实例（`app`），通过 Supertest 发起请求，无需启动 HTTP 服务器监听端口
- **断言规范**：每个测试用例至少断言响应状态码和响应体关键字段。正常场景断言数据结构与内容合理性；异常场景断言错误码与错误信息
- **测试执行时间**：全部测试用例执行完毕 <= 30s
- **CI 兼容**：测试文件检测数据库文件是否存在，不存在时跳过并输出提示（避免 CI 环境无数据库导致全部失败）
- **ESM 兼容**：项目使用 `"type": "module"`，测试文件使用 ESM 语法（`import`/`export`），Vitest 原生支持

#### 异常场景

| 场景 | 处理方式 |
|---|---|
| poetry.db 数据库文件不存在 | 测试文件开头检测数据库是否存在，不存在时调用 `describe.skip()` 跳过全部用例并输出提示"数据库文件不存在，跳过测试" |
| 数据库文件损坏或格式不正确 | 测试用例捕获数据库异常，标记对应用例为失败并输出错误详情 |
| 后端 API 变更导致测试失败 | 测试失败输出详细的期望值 vs 实际值对比，帮助开发者定位变更影响 |
| 测试端口冲突 | Supertest 使用随机端口或无需监听端口（直接引用 app 实例），不存在端口冲突问题 |
| 测试执行超时 | Vitest 配置合理的超时时间（单用例默认 5s），避免单个慢用例阻塞全部测试 |

## 七、排他说明

### 7.1 二期不做的功能

以下功能明确不纳入二期范围，与总体方案 2.2 节保持一致：

| 排除项 | 原因 |
|---|---|
| AI 诗词赏析与配图 | 需外部 AI API 接入，成本和可用性不确定，非"好用易用"核心诉求 |
| 社区互动（评论/分享/讨论） | 功能过重，需用户系统前置，与"轻量"定位冲突 |
| 公网部署 | 基础设施投入，不影响本地使用体验，二期聚焦功能体验而非运维 |
| 用户注册/登录系统 | localStorage 收藏已满足核心个性化需求，无需引入账号体系的复杂度 |
| 收藏夹导出与分享 | 依赖社交场景，非二期"好用易用"核心目标 |
| 诗词背诵/默写模式 | 教育类需求，与二期阅读/搜索体验优化方向不同 |

### 7.2 不做的原因总结

1. **聚焦核心价值**：二期目标是"好用易用"，上述排除项均不属于体验优化的核心范畴
2. **控制开发成本**：AI 集成、用户系统、社区功能均显著增加开发工作量和复杂度
3. **保持零侵入**：二期不新增后端 API，对后端零侵入，降低回归风险（AC14）
4. **降低技术风险**：不引入外部 AI 服务依赖、不增加数据库变更、不投入服务器成本
5. **三期可平滑扩展**：上述功能已在三期展望中记录，可基于二期架构逐步扩展
